# Хостинг, SEO, миграция с Tilda и админка

Заметки о том, как работает публикация сайта через GitHub Pages, что с SEO, стоит ли уходить с Tilda и можно ли сделать админку на Tauri.

## 1. Как работает публикация

Astro здесь работает как **build-time** генератор, а не в runtime.

Пайплайн ([.github/workflows/deploy.yml](../.github/workflows/deploy.yml)):

1. Пуш в `main` запускает GitHub Actions.
2. Runner делает `npm ci`: `astro`, `sharp` и шрифты ставятся в `node_modules` на CI-машине.
3. `npm run build` (`astro build`) собирает статику в `dist/`: HTML, CSS, JS, оптимизированные картинки.
4. В Pages загружается только `dist/`.

Что важно:

- На хостинг попадает только статика. `node_modules` не публикуется и нужен только на этапе сборки.
- `node_modules` не лежит и в git (он в `.gitignore`). Зависимости каждый раз ставятся по `package-lock.json`.
- GitHub Pages не выполняет серверный код. SSR и серверные эндпоинты Astro там не заработают.
- Текущий конфиг (`defineConfig` без адаптера) использует режим `static`, поэтому проблем нет.
- Шрифты `@fontsource` при сборке копируются в `dist` как обычные файлы.
- Для SSR понадобится другой хостинг (Vercel, Netlify) и адаптер Astro.

## 2. SEO на GitHub Pages

Схема SEO-friendly: поисковик получает готовый HTML с контентом без выполнения JS, Astro почти не отдаёт JS, Pages раздаёт файлы через CDN, HTTPS включён по умолчанию.

Что нужно сделать самим:

- Уникальные `<title>` и `<meta name="description">` на каждой странице.
- Open Graph и Twitter-теги для превью в соцсетях и мессенджерах.
- `<link rel="canonical">`. В конфиге уже есть `site`, значит абсолютные URL строятся.
- Sitemap (интеграция `@astrojs/sitemap`) и `robots.txt` в `public/`.
- `alt` у картинок, один `h1`, осмысленная иерархия заголовков.
- Регистрация в Google Search Console и Яндекс Вебмастере, отправка sitemap.

Ограничения Pages:

- Нельзя настроить серверные редиректы и HTTP-заголовки. Опция `redirects` в конфиге Astro создаёт HTML с meta refresh, это хуже, чем 301.
- Свой 404 работает через `404.astro` или `404.html`.
- Адрес `shdr-videos.github.io` это поддомен github.io. Для бренда лучше подключить свой домен (`shdr.online`): файл `public/CNAME` и обновлённое `site` в `astro.config.mjs`.

## 3. Стоит ли уходить с Tilda

Да, если сайт в основном контентный (витрина, портфолио, лендинги) и вы готовы вести его в коде.

Что выигрываем:

- **Скорость и SEO.** Tilda подгружает много лишнего JS и CSS, статика на Astro обычно быстрее и лучше проходит Core Web Vitals.
- **Стоимость.** GitHub Pages бесплатен, платный тариф Tilda с собственным доменом и экспортом около $10–20 в месяц.
- **Контроль.** Вёрстка, мета-теги, URL, редиректы, аналитика полностью в наших руках.
- **Версионирование.** Все изменения в git, есть история и откат.
- **Дизайн** превью уже переработан.

Что теряем:

- Визуальный редактор. Любая правка идёт через код и деплой, для не-разработчиков нужна CMS.
- Встроенные формы, оплату и CRM-интеграции Tilda. Замена: Formspree, Web3Forms, Netlify Forms, отдельные платёжные сервисы.
- Серверную часть: всё динамическое нужно выносить во внешние сервисы.

Риски миграции:

- **Потеря позиций в поиске.** Сохранить старые URL или настроить редиректы со старых адресов на новые.
- **Домен.** Переключать DNS в последний момент, когда новый сайт готов и проверен.
- **Старый проект на Tilda** не удалять, пока новый не отработает пару недель.

Рекомендация:

- Статичный сайт, который поддерживаем сами: переносим.
- Контент часто правят нетехнические люди, много форм и интеграций: сначала подключить CMS.
- Если заявки приходят через формы Tilda, заранее решить, чем их заменить.

## 4. Админка на Tauri с деплоем через GitHub Pages

Схема рабочая.

- Tauri-приложение даёт форму или редактор контента.
- Приложение коммитит изменения в репозиторий через GitHub API (REST/GraphQL) либо через локальный git (`git2` в Rust или вызов `git`).
- Пуш в `main` запускает [deploy.yml](../.github/workflows/deploy.yml), сайт пересобирается и публикуется.

Что для этого нужно:

- **Контент в файлах, а не в коде страниц.** Astro Content Collections (Markdown/MDX или JSON/YAML), админка правит данные, а не вёрстку.
- **Картинки** кладутся в репозиторий (`src/assets` или `public`), `sharp` оптимизирует их при сборке.
- **Авторизация.** Fine-grained Personal Access Token на один репозиторий с минимальными правами либо GitHub OAuth device flow. Токен хранить в системном хранилище (keychain), не в файле.

Плюсы:

- Админка не публикуется в интернет, её нельзя взломать через сайт.
- Бесплатно, серверной части нет.
- Интерфейс под наши задачи (например, загрузка видео, превью).
- Правки идут через git: история и откат.

Минусы:

- Отдельное приложение, которое нужно писать, поддерживать, собирать и подписывать под macOS и Windows. Без подписи ОС показывает предупреждения.
- Каждому редактору нужно установить приложение и получить доступ к репозиторию. Мобильного доступа нет.
- Задержка между правкой и публикацией 1–3 минуты на сборку.
- Живой предпросмотр из коробки отсутствует (можно запускать `astro dev` внутри приложения).

Готовые альтернативы, которые стоит оценить сначала:

- **Decap CMS** или **Keystatic**: веб-админка, коммитит в git, работает с Pages, нужен небольшой OAuth-прокси.
- **Sanity** или **Contentful**: headless CMS, сайт пересобирается по вебхуку.
- **Tina CMS**: git-based, есть визуальное редактирование.

Вывод:

- Правим только мы или небольшая команда на десктопе, нужен нестандартный интерфейс (например, под видео): Tauri оправдан.
- Несколько редакторов, не технари или нужен доступ с телефона: готовая git-based CMS закроет задачу за часы, а не недели.
